## Context

旧版 QT 锁模白名单不提交子作业状态，ERP 仅在父作业已存在时把新增子作业设为 `status=1`；首次锁模产生的合法待开始缓存因此是父作业 `id=null,status=0`、子作业 `id=null,pressJobInfoId=null,status=null`。当前锁模、`START` 和解锁入口在懒持久化前要求子作业状态等于父作业状态，使存量待开始作业无法继续任何生命周期操作。

当前 ERP 已有设备绑定行锁、父子懒持久化、真实 ID 回写和解锁 `status=4` 事务路径。本 hotfix 只补齐旧版真实数据形状，不引入第二套迁移机制。

## Goals / Non-Goals

**Goals:**

- 旧版合法待开始 JSON 在下一次锁模、`START` 或解锁时自动兼容，无需现场清场。
- 兼容发生在现有设备行锁事务内，生成真实父子 ID 后继续当前业务动作。
- 保持设备、授权主机、父子关系、模具号唯一性和状态边界的严格校验。

**Non-Goals:**

- 不批量扫描或回填设备、父作业、子作业数据。
- 不兼容跨设备、跨主机、冲突 ID、重复模具或未知状态等无法证明归属的数据。
- 不修改 QT App、Driver Service、HTTP contract、数据库 schema 或操作日志体系。

## Decisions

### 1. 只规范化旧代码能够生成的窄数据形状

只有父作业满足 `id=null,status=0`，且子作业同时满足 `id=null,pressJobInfoId=null,status=null` 时，服务端才把该子状态规范化为 `0`。设备、授权主机、模具号和其他身份校验继续由现有严格校验执行；包含真实 ID、非空冲突状态或其他混合形状的数据不得进入该分支。

选择该方式而不是放宽通用状态比较，是因为空子状态来自已确认的旧写入行为，而其他不一致仍可能表示陈旧缓存或错误归属。

### 2. 复用现有事务内懒持久化

锁模和 `START` 在状态规范化后继续使用现有父子懒持久化逻辑。解锁在选择和更新模具前，复用相同的待开始父子持久化路径写入真实 ID 并同步设备 JSON，然后按既有部分/全部解锁规则更新 `status=4`。

不新增离线脚本或迁移端点；每台设备只在下一次真实业务动作中处理自己的当前作业，事务失败时父子写入和设备 JSON 一起回滚。

### 3. 回归测试固定旧生产者形状和安全反例

测试直接构造旧版父 `status=0`、子 `status=null` 且父子 ID 为空的缓存，分别覆盖继续锁模、`START`、部分解锁和全部解锁。另保留或补充带 ID、跨设备/主机、重复模具和非待开始状态的写前拒绝断言，证明兼容分支没有扩大信任边界。

## Risks / Trade-offs

- [把未知空状态误当成旧数据] → 仅允许父子 ID 全空、父状态为 `0` 的窄形状，并继续执行设备、主机和模具唯一性校验。
- [解锁先持久化再终止产生中间状态] → 两步位于同一数据库事务且设备行已锁定，任一步失败全部回滚。
- [重复动作再次插入] → 第一次成功后真实 ID 已回写设备 JSON，后续动作走正常持久化分支。

## Migration Plan

1. 先部署 ERP hotfix；不执行数据库脚本，也不要求工控机结束当前作业。
2. 每个旧待开始作业在下一次锁模、`START` 或解锁时自动规范化并懒持久化一次。
3. 新版本产生的完整 `status=0` 和真实 ID 数据保持原路径不变。
4. 回滚到本 hotfix 前版本不需要数据库 rollback；已持久化的 `status=0/4` 使用既有 schema。
